`tools/kt-mcp` is a standard-library Python stdio MCP server, installed to `~/.knowledge/.tools/kt-mcp`, that exposes the kt workflow as 23 low-friction tools, meant to be used instead of the `kt` shell command. The CLI owns knowledge, lifecycle, revision, and access semantics; MCP is the typed harness adapter. Operations delegate to the sibling `kt` with stdin closed. Access elicitation is the narrow adapter-owned exception because it is a server-to-client protocol exchange.

Successful `kt_rewrite` calls return the answer diff followed by `Revision: HASH`, including unchanged no-ops. Reuse that committed hash for the next rewrite without reading back the answer already in context. Dry runs return only a preview and no new revision. The CLI supplies the committed hash under the write lock via `--print-revision`; MCP remembers the supplied whole answer for renewal and undo without a post-write read. If another writer changes the leaf, the next rewrite rejects the stale hash; reread and merge then. Renewal still requires verification of the whole answer, but no redundant read after a successful rewrite.

**Tools.** Retrieval and inspection: `kt_lookup`, `kt_find`, `kt_grep`, `kt_read`, `kt_dict`, `kt_roots`, `kt_status`, `kt_audit`, and `kt_access_status`. `kt_audit` reports bodies over 1,000 words as suspect and date-shaped bodies as quite-suspect without changing lifecycle state. Change: `kt_add` establishes a missing current answer; `kt_rewrite` recomputes an existing answer from a whole-read hash and can set or clear expiry and proof-coverage metadata. The old body is material to reconsider, not a template to extend. Revision-guarded remove, move, combine, undo, renew, initialization, registration, and proof tools retain CLI semantics. Access tools request, complete, inspect, and revoke grants without granting the model authority to answer user prompts.

**Growth bounces.** The CLI owns bounded long-leaf growth enforcement: one rejection beyond 500 body words, two above 1,000, three above 2,000; severity uses the larger current/proposed body. Short or shorter replacements pass immediately; remaining growth can pass after the bounded rejections. MCP surfaces CLI exit 5 as a tool error, preserves the revision, and records no undo entry for rejection. Counters survive process restarts outside the tree; previews consume no attempts. Reconsider the whole answer before retrying. See `how/to/rewrite/a/knowledge/leaf.md` for the precise contract. Undo and combine into an existing destination share the CLI rewrite guard.

**Lean output and renewal.** Front matter, timestamps, and status stamps stay hidden. A whole-leaf MCP read shows only the answer, an optional non-green notice, and its Revision hash. `kt_rewrite` takes that explicit hash; knowing it establishes that the caller obtained the complete version, while the locked CLI check rejects intervening changes. `kt_renew` additionally uses the server's remembered whole answer. `kt_renew` records `checked_at` and reruns the leaf's proofs. The shell has the same whole-read contract: `kt open` and exact question hits print the complete leaf and hash; search excerpts are never reads.

**Annotations and results.** Every tool carries MCP annotations (`readOnlyHint` on retrieval/audit tools; `destructiveHint` on replacement and removal; `openWorldHint` false). A miss or brown result is data marked `(exit 1)`; only exit 2 or higher is a tool error. Initialization instructions state the frontier contract at the mutation boundary. User prompts are `frontier_review`, `garden`, `verify_leaf`, and `revoke_access`; gardening combines lifecycle status with structural audit and never treats an audit signal as a diagnosis.

**Still terminal-only:** direct `access` policy changes and the global `permissions` bypass. Access approval and revocation use the guarded MCP tools; whole-leaf review is `kt_renew`.

**Access approval by elicitation.** `kt_access_request` accepts a root, honest reason, and optional least-sufficient preferred scope. The user still chooses. When the harness supplies `KT_SESSION_ID`, `CODEX_THREAD_ID`, or `OPENCODE_SESSION_ID`, temporary session access is offered alongside project, project-with-descendants, and everywhere scopes. Only an accepted elicitation persists a grant through the CLI's `apply_access_decision`; the model never answers the prompt. Deny and force-private never prompt. Unrendered decline, cancel, invalid response, client error, or absent elicitation returns a bound one-time continuation and changes nothing; only explicit conversational authorization for its exact root and scope permits `kt_access_confirm`.

**Revocation and stale approvals.** `kt_access_status` says why each root is readable. `kt_access_revoke` removes a session grant directly, narrows this project directly, and asks before a wider or global change; failed elicitation has the same bound conversational continuation. Local-tree access and the permissions bypass remain terminal-owned. Path-keyed stale approvals are pruned so recreated trees need fresh authorization.

**Registration.** `./install` registers the server: Codex `[mcp_servers.knowledgetrees]` in `~/.codex/config.toml`, OpenCode `mcp.knowledgetrees` in `opencode.json`, Copilot CLI `mcpServers.knowledgetrees` in `~/.copilot/mcp-config.json`, and Claude Code through `claude mcp add --scope user` (its own config file is never edited directly). Existing registrations under that name are left alone, other MCP servers are preserved, and `--no-mcp` skips everything. Restart each harness to load it. The server runs in the harness's working directory, so `local:` addresses resolve there; `KT_MCP_PROJECT_DIR` or `CLAUDE_PROJECT_DIR` selects the project when a user-scoped server starts elsewhere.

**Verification and live limits.** `tests/test-mcp.py` covers all 23 tools, schemas, annotations, rewrite lifecycle parity, growth bounces and undo integrity, structural audit, revision guards, prompts, and access flows including session/project/inherited/everywhere grants, direct and confirmed revocation, denied/force-private roots, failed-elicitation continuations, and concurrent requests. Freshly restarted clients still require live observation before claiming a newly installed build is loaded.
