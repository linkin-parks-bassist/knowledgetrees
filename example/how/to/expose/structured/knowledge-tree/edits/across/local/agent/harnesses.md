`tools/kt-mcp` is a standard-library Python stdio MCP server, installed to `~/.knowledge/.tools/kt-mcp`, that exposes the kt workflow as 20 tools, meant to be used instead of the `kt` shell command (the shell is the fallback when the tools are unavailable). Every operation runs the sibling `kt` in a subprocess (stdin closed, arguments after `--`), so revision conflicts, access policy, locking, proof invalidation, and inode preservation stay owned by the CLI. The one exception is access approval, below.

**Tools.** Retrieval (read-only): `kt_lookup`, `kt_find`, `kt_grep`, `kt_read`, `kt_dict`, `kt_roots`, `kt_status`, and `kt_access_status`. `kt_read` and exact lookup hits always return the complete answer plus a final `Revision:` SHA-256 line; there are no partial reads, ranges, paging, or truncation. Ranked excerpts are selectors, not reads, and expose no rewrite hash. Change: `kt_rewrite` is the standard editing tool and replaces the complete answer only when given the hash from a whole read; the CLI rejects a stale hash under lock. Use `kt_edit` only for economy on a tiny surgical exact-match change. `kt_rm` and `kt_mv` require the source read hash; `kt_init` initializes only the current MCP project, registers the new tree under `ask` without a grant, and refuses an existing tree. `kt_undo` restores this session's last rewrite or edit while unchanged; `kt_add` creates a leaf; `kt_renew` confirms a verified whole leaf. Other tools are `kt_prove`, `kt_info`, `kt_access_request`, and `kt_access_revoke`.

**Lean output and renewal.** Front matter, timestamps, and status stamps stay hidden. A whole-leaf MCP read shows only the answer, an optional non-green notice, and its Revision hash. `kt_rewrite` takes that explicit hash; knowing it establishes that the caller obtained the complete version, while the locked CLI check rejects intervening changes. `kt_edit` and `kt_renew` additionally use the server's remembered whole answer. `kt_renew` records `checked_at` and reruns the leaf's proofs. The shell has the same whole-read contract: `kt open` and exact question hits print the complete leaf and hash; search excerpts are never reads.

**Annotations and results.** Every tool carries MCP annotations (`readOnlyHint` on the retrieval tools; `destructiveHint` on edit and undo; `openWorldHint` false) so harnesses can skip prompts for reads and keep them for writes. A miss or brown result is data marked `(exit 1)`; only exit 2 or higher is a tool error. The server also sends short `instructions` at initialization and four prompts a user can invoke: `capture_review`, `garden`, `verify_leaf`, and `revoke_access`.

**Not exposed:** `combine`, `register`, `access`, and `permissions`; whole-leaf review is `kt_renew`.

**Access approval by elicitation.** `kt access` needs an interactive terminal confirmation, and `kt_access_request` is the in-harness equivalent: it sends an MCP `elicitation/create` request to the client, asking it to show a prompt naming the root, the project directory, and the agent's reason (control characters stripped, 300 characters), with three choices: this project directory, this project and subdirectories, or everywhere. Only an accepted response carrying one of those scopes persists the grant, through the CLI's own `apply_access_decision`. The model never sees or answers the MCP prompt. Session scope is not offered because the server cannot know the agent's session id. Denied roots and force-private roots are never prompted for (the latter reveal nothing), and an already-allowed root needs no prompt. A client may advertise elicitation yet return decline, cancel, or an error without visibly prompting; the server reports the client action without claiming the user declined, does not cache it as a refusal, and supplies the exact interactive `kt access` fallback. A client that did not declare elicitation gets the same fallback immediately. If the user explicitly authorizes the exact root and scope in conversation, the agent may run and confirm that CLI command in an interactive terminal; otherwise the user does it. A failed prompt is not a prohibition on acting on a later explicit authorization. There is no CLI flag that skips the terminal prompt. This is a guardrail against an agent inventing its own access decision, not a sandbox: an agent that can run arbitrary commands as the same user can already edit the policy files, so the real boundary is what your harness lets the agent run.

**Revocation and stale approvals.** Access used to only grow, so `kt_access_status` (backed by the CLI's `kt grants`) now says why each root is readable: local tree, project grant (with the directory that made it), allowed everywhere, session grant, permissions bypass, denied, or needing approval; it marks a root whose tree no longer exists. `kt_access_revoke` gives access back: scope `project` (default) makes the root require approval again in this project, overriding an everywhere-allow for this project only; scope `all` does so everywhere, removes every project grant for the root, or removes the registration of a root whose tree is gone. Narrowing this exact directory is done directly, since it only reduces reach and asking again prompts the user; anything wider (scope `all`, a grant inherited from a parent directory, or the global root) asks the user to confirm first, and a client that cannot prompt gets the terminal command `kt access ROOT revoke --scope all`. The local tree, a permissions bypass, and a session grant cannot be revoked this way. Approvals are keyed by path, so `kt` prunes them when a tree disappears: on every run it drops project grants whose project directory or root no longer exists registered roots that were allowed everywhere, and auto-named `root-<hash>` ask registrations (which name nothing but a dead path), with a one-line stderr notice, so a different tree later recreated at the same path needs a fresh approval. Deny and force-private entries and user-named ask registrations are kept (they protect or name a tree, and it may be unmounted); `kt grants` marks them missing and revoking with scope `all` removes one. A tree deleted and recreated between two `kt` runs, before any pruning, is not detected.

**Registration.** `./install` registers the server: Codex `[mcp_servers.knowledgetrees]` in `~/.codex/config.toml`, OpenCode `mcp.knowledgetrees` in `opencode.json`, Copilot CLI `mcpServers.knowledgetrees` in `~/.copilot/mcp-config.json`, and Claude Code through `claude mcp add --scope user` (its own config file is never edited directly). Existing registrations under that name are left alone, other MCP servers are preserved, and `--no-mcp` skips everything. Restart each harness to load it. The server runs in the harness's working directory, so `local:` addresses resolve there; `KT_MCP_PROJECT_DIR` or `CLAUDE_PROJECT_DIR` selects the project when a user-scoped server starts elsewhere.

**Verified.** Lean output, read-before-edit, answer-based staleness, and renew are covered by `tests/test-mcp.py` and `tests/test-metadata.py` but have not yet been observed in a live harness session. Protocol tests (`tests/test-mcp.py`) and CLI tests (`tests/test-grants.py`, covering source reporting, revocation, and pruning) cover every tool, the annotations, atomic multi-edit, undo refusal after a hand edit, JSON find, option-injection guards, prompts, and the elicitation flow with a fake client (accept in all three scopes; decline, cancel, and client-error fallback without false user attribution or retry suppression; invalid answers; no prompt for denied or force-private roots; revocation with direct, confirmed, declined, and no-capability paths; a request arriving mid-prompt still served; no grant before an accepted response). The owner reported the original tools working in live Codex and OpenCode sessions on 2026-09-20 (not independently observed). Verified live in Claude Code (2026-09-20, owner-observed): a `kt_access_request` on a throwaway restricted root showed the owner an approval prompt in the terminal, the owner's accept persisted a project grant (the model could then read the root and `kt_access_status` reported `project grant`), and `kt_access_revoke` narrowed the current directory directly with no second prompt, after which the root was unreadable again and no project grant remained. A headless `claude -p` session, which cannot show a prompt, fails closed (the client returns decline and the policy file is unchanged). On 2026-09-21 Codex advertised elicitation but returned decline without displaying any prompt; this established the need for truthful client-action reporting and terminal fallback, but did not establish why Codex failed to render it.
