`tools/kt-mcp` is a standard-library Python stdio MCP server, installed to `~/.knowledge/.tools/kt-mcp`, that exposes the kt workflow as 16 tools. Every operation runs the sibling `kt` in a subprocess (stdin closed, arguments after `--`), so revision conflicts, access policy, locking, proof invalidation, and inode preservation stay owned by the CLI. The one exception is access approval, below.

**Tools.** Retrieval (read-only): `kt_lookup` (natural questions like `how to ...`; `how to _` lists a branch), `kt_find` (optional `json` returns structured `{address, coverage, weak, status, excerpt}` results), `kt_grep` (literal or regex text search across readable roots, with `regex`, `ignore_case`, `files_only`, `context`, `limit`), `kt_read` (revision plus text; `body_only`, and `offset`/`limit` characters to page long leaves), `kt_dict`, `kt_roots`, `kt_status` (non-green leaves with reasons, no proofs run), and `kt_access_status`. Change: `kt_edit` replaces exact text that must match once in the answer body against the revision you read, with either `old_text`/`new_text` or an `edits` array applied atomically in order (any failure writes nothing); `kt_rewrite` replaces a whole body; `kt_undo` restores the body from before this session's latest edit of a leaf, only if the leaf is unchanged since (history is in memory, last 20 edits, lost on restart); `kt_add` creates a leaf (local or global) and refuses to overwrite an owner. Other: `kt_prove` (does not stamp unless `stamp` is set), `kt_info` (the startup output; it runs a proof pass, which refreshes leaf status stamps), `kt_access_request`, and `kt_access_revoke`.

**Annotations and results.** Every tool carries MCP annotations (`readOnlyHint` on the retrieval tools; `destructiveHint` on edit, rewrite, and undo; `openWorldHint` false) so harnesses can skip prompts for reads and keep them for writes. A miss or brown result is data marked `(exit 1)`; only exit 2 or higher is a tool error. The server also sends short `instructions` at initialization and four prompts a user can invoke: `capture_review`, `garden`, `verify_leaf`, and `revoke_access`.

**Not exposed:** `rm`, `mv`, `combine`, `register`, `access`, `permissions` (destructive or policy-changing), and `check` and `init` (whole-leaf review and initialization stay with the CLI).

**Access approval by elicitation.** `kt access` needs the user's own interactive terminal, and `kt_access_request` is the in-harness equivalent: it sends an MCP `elicitation/create` request to the client, which shows the user a prompt naming the root, the project directory, and the agent's reason (control characters stripped, 300 characters), with three choices: this project directory, this project and subdirectories, or everywhere. Only the user's accept persists the grant, through the CLI's own `apply_access_decision`; decline or cancel changes nothing. The model never sees or answers the prompt. Session scope is not offered because the server cannot know the agent's session id. Denied roots and force-private roots are never prompted for (the latter reveal nothing), an already-allowed root needs no prompt, and a root the user declined is not asked about again that session (there is deliberately no numeric cap on prompts). A client that did not declare the `elicitation` capability gets the exact terminal command instead. There is no CLI flag that skips the terminal prompt. This is a guardrail against an agent granting itself access, not a sandbox: an agent that can run arbitrary commands as the same user can already edit the policy files, so the real boundary is what your harness lets the agent run.

**Revocation and stale approvals.** Access used to only grow, so `kt_access_status` (backed by the CLI's `kt grants`) now says why each root is readable: local tree, project grant (with the directory that made it), allowed everywhere, session grant, permissions bypass, denied, or needing approval; it marks a root whose tree no longer exists. `kt_access_revoke` gives access back: scope `project` (default) makes the root require approval again in this project, overriding an everywhere-allow for this project only; scope `all` does so everywhere, removes every project grant for the root, or removes the registration of a root whose tree is gone. Narrowing this exact directory is done directly, since it only reduces reach and asking again prompts the user; anything wider (scope `all`, a grant inherited from a parent directory, or the global root) asks the user to confirm first, and a client that cannot prompt gets the terminal command `kt access ROOT revoke --scope all`. The local tree, a permissions bypass, and a session grant cannot be revoked this way. Approvals are keyed by path, so `kt` prunes them when a tree disappears: on every run it drops project grants whose project directory or root no longer exists registered roots that were allowed everywhere, and auto-named `root-<hash>` ask registrations (which name nothing but a dead path), with a one-line stderr notice, so a different tree later recreated at the same path needs a fresh approval. Deny and force-private entries and user-named ask registrations are kept (they protect or name a tree, and it may be unmounted); `kt grants` marks them missing and revoking with scope `all` removes one. A tree deleted and recreated between two `kt` runs, before any pruning, is not detected.

**Registration.** `./install` registers the server: Codex `[mcp_servers.knowledgetrees]` in `~/.codex/config.toml`, OpenCode `mcp.knowledgetrees` in `opencode.json`, Copilot CLI `mcpServers.knowledgetrees` in `~/.copilot/mcp-config.json`, and Claude Code through `claude mcp add --scope user` (its own config file is never edited directly). Existing registrations under that name are left alone, other MCP servers are preserved, and `--no-mcp` skips everything. Restart each harness to load it. The server runs in the harness's working directory, so `local:` addresses resolve there; `KT_MCP_PROJECT_DIR` or `CLAUDE_PROJECT_DIR` selects the project when a user-scoped server starts elsewhere.

**Verified.** Protocol tests (`tests/test-mcp.py`) and CLI tests (`tests/test-grants.py`, covering source reporting, revocation, and pruning) cover every tool, the annotations, atomic multi-edit, undo refusal after a hand edit, JSON find, option-injection guards, prompts, and the elicitation flow with a fake client (accept in all three scopes, decline, cancel, invalid answer, no prompt for denied or force-private roots, no re-nagging, revocation with direct, confirmed, declined, and no-capability paths, a request arriving mid-prompt still served, no grant before the user answers). The owner reported the original tools working in live Codex and OpenCode sessions on 2026-09-20 (not independently observed). Verified live in Claude Code (2026-09-20, owner-observed): a `kt_access_request` on a throwaway restricted root showed the owner an approval prompt in the terminal, the owner's accept persisted a project grant (the model could then read the root and `kt_access_status` reported `project grant`), and `kt_access_revoke` narrowed the current directory directly with no second prompt, after which the root was unreadable again and no project grant remained. A headless `claude -p` session, which cannot show a prompt, fails closed (the request comes back declined and the policy file is unchanged). Not yet verified live: elicitation in Codex, OpenCode, and Copilot CLI (whether they declare the capability and how they render the choices is unknown), the wider revoke paths (scope all, the global root) with a real prompt, and Copilot CLI at all.
